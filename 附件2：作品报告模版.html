第三章　作品测试与分析

3.1 测试目标与验证原则

本项目的测试目标并不是"系统能否生成攻击文本"，也不是"是否收到 HTTP 200"，而是"系统能否在受控条件下产出可被独立复核的真实执行证据，并据此做出可信的成功判定"。这一目标决定了本章全部测试设计的基本立场：以可观测、可复现的客观证据为依据，而不是以模型自述、历史记忆或过程性日志为依据。

为此，本章在测试中严格区分以下五个层次的概念，它们在本系统中具有不同的证据强度，不可互相替代：

  • 请求可达：目标服务在网络与传输层可达，例如收到 HTTP 响应。它仅说明"对方在"，不代表漏洞相关行为发生。
  • 参数实际送达：构造的请求按约定的方法、路径与请求体把目标参数送到了服务端，而非被丢弃或退化为默认页面。这一层是后续一切验证的前提。
  • 漏洞原语被观察到：在响应中观察到与漏洞机制直接相关的可识别原语，例如模板引擎对受控表达式的求值回显，说明该机制确实被触发。
  • 能力或影响被确认：原语进一步转化为可证明的能力，例如执行了受控运算、读取了受控内容。这一层比原语更强，但仍不等同于最终任务目标。
  • 最终目标被验证：在当前轮完整真实响应中出现任务定义的最终目标证据（如约定格式的目标标记），并由确定性目标裁决层独立确认。

基于上述区分，测试设计采用"静态线索 + 动态受控验证 + 独立目标裁决"的闭环：静态线索指明 source、sink 与参数关系；动态受控验证在沙箱中以低风险载荷逐层确认；独立目标裁决只采信当前轮真实执行响应。系统不把 Planner 的推理文本（rationale）、计划正文、历史 memory、上一轮 feedback 或旧 workspace 文件当作最终成功证据。

3.2 测试环境与边界条件

测试在以下基础环境中进行：宿主机为 Windows 11，Python 运行环境通过项目 requirements.txt 约束依赖，容器运行依赖 Docker Desktop，大模型推理通过 OpenAI 兼容接口访问。靶场应用本身以容器形式在本地授权环境中运行，Co-RedTeam 的执行器另起独立 Docker 容器对其发起受控请求。Executor 在独立 Docker 沙箱中隔离执行，并通过容器层面的权限收敛与资源限制等运行时安全约束降低执行风险（具体配置见 b/agents/executor.py 与 b/Dockerfile）。

目标边界通过 Target Context Lock 实现：Coordinator 启动时调用 lock_target()，对传入的授权 URL 做协议校验（仅允许 http/https）、主机名校验、DNS 解析与规范化，固化 base_url 并写入 confirmed_vuln.json 的 target_context；Executor 仅使用该锁定地址。所有测试均在授权靶场进行，不涉及真实互联网资产。

关于成功判定范围，本系统仅以当前轮执行结果作为成功判定的证据来源；历史轮次的输出不直接构成当前成功证据。本次测试聚焦于 5 个典型入门级 Web 安全挑战，旨在验证系统从结构化规划、受控执行到目标证据确认的端到端闭环能力。

案例背景与静态线索。在 b/data/confirmed_vuln.json 中，漏洞条目给出 source（HTTP GET/POST text 参数通过 @RequestParam 接收）、sink（RuntimeServices.parse(reader, "home") 与 t.merge(context, writer)），并通过数据流逐步描述：用户输入的 text 被传入文件读取函数，经 line.replace("TEXT", replacement) 替换占位符后嵌入模板字符串，随后被 StringReader 包装并由 Apache Velocity 解析、渲染。这条数据流明确了"用户输入在模板解析前被拼接"这一关键事实。仅凭静态线索不能直接宣布漏洞成功，因为从 source 到 sink 的可达性、参数是否真的送达、模板是否真的被解析，都必须由动态执行证据来确认。

端到端验证流程。系统在该案例上沿以下链路完成受控验证：

静态漏洞线索 → 参数契约确认 → 结构化 POST 请求 → 参数实际送达 → 低风险表达式解析证据 → 当前轮真实 HTTP response body 出现最终目标证据 → GoalVerifier 确认 → 生成 success_summary.json 与 Victory Screen → 立即停止

对该流程的各环节说明如下。第一，静态漏洞线索指明 source、sink、参数与模板解析关系，作为后续验证的依据。第二，参数契约确认：系统把请求意图固化为物化的请求契约（方法、端点、参数列表、规范化请求体及其指纹），与漏洞线索逐字段比对，确认"POST + text 参数"的意图被正确表达。第三，结构化 POST 请求：Executor 把声明式请求描述编译为一次 POST /，请求体为表单格式且包含 text 字段，对应目标接口的真实线缆行为。第四，参数实际送达：当响应不再是空参数的默认页面、且能反映受控输入时，判定参数已送达服务端解析路径；若仅返回默认页面、输入框 value 为空，则判定请求未按契约送达并回落修复。第五，低风险表达式解析证据：请求体中携带一个低风险模板表达式（如对两个整数做乘法并输出结果），若其求值结果出现在响应体中，则说明 Velocity 模板引擎对用户输入进行了解析与求值，模板注入原语被客观观察到。第六，最终目标证据：任务定义的最终目标证据必须出现在当前轮完整的真实 HTTP response body 中。第七，GoalVerifier 确认：由独立于模型推理的确定性目标裁决器（b/core/goal_verifier.py，verify_goal()）只从当前轮真实响应中取证（允许证据源仅限 chain_output._last_response_text、_http_responses[*].response_body 与 http_responses[*].response_body），显式排除 Planner rationale、计划正文、历史 memory 与旧产物；同时通过回显排除（anti-echo）防止请求内字符串被误判为服务端产出。第八，生成 success_summary.json 与 Victory Screen 并立即停止：GoalVerifier 命中后，系统写入 success_summary.json（含验证版本、flag、证据哈希、来源类型等字段）并渲染 Victory Screen（b/ui/victory_screen.py，render_victory_screen()），Coordinator 执行 return 0 立即结束迭代——Evaluator 在成功路径上被完全跳过，不产生 LLM 调用、不产生多余的 [FAILED] 覆写或预算消耗。

3.4 测试流程与关键运行链路

系统在测试中沿以下真实链路运行，每一步都落盘可审计的产物文件：

Planner → plan.json → Validator → validated_plan.json → Docker Executor → execution_result.json → GoalVerifier（确定性裁决）→ [命中] success_summary.json + Victory Screen + return 0
　　↘ [未命中] Evaluator → feedback.json → 下一轮 Planner

各文件的责任与审计价值如下。plan.json 是 Planner 输出的结构化计划，记录所选策略、各步骤类型、用途、预期结果与依赖关系，以及历史状态透传字段；其审计价值在于"系统打算做什么"是被显式记录的。validated_plan.json 记录校验结论（通过/错误、告警、是否做过归一化）与通过校验的计划；其审计价值在于"什么计划被允许进入执行"有据可查。execution_result.json 记录每一步的执行模式（docker / security_blocked）、退出码、stdout/stderr、容器 ID、物化请求契约与完整 HTTP 响应；其审计价值在于"执行线缆上实际发生了什么"被完整捕获。feedback.json 记录本轮的判定、证据层级、状态机位置与对下一轮的指导。success_summary.json 由 Victory Screen 在目标确认后写入，汇总验证版本、目标证据、证据哈希、来源类型与步骤编号等字段，供复盘与展示；Victory Screen 则以 Rich 终端 UI 渲染胜利结算 HUD。即便失败，plan、validated_plan、execution_result、feedback 也均落盘，保留可复盘的过程信息。

对链路中各模块的职责边界需作如下澄清，这些边界是本系统可答辩性的关键：

  • Planner 输出的是结构化计划，不等于执行。计划只是意图，必须经校验与编译后才可能被执行，且 Planner 不拥有宣布成功的权力。
  • Validator 对语法树、允许能力与参数契约进行约束。它用 ast.parse 检查语法，用导入白名单与危险模式黑名单约束能力，对结构化请求进行契约层面核验；不满足要求的计划在执行前即被阻断。
  • Executor 只在沙箱中执行核验通过的计划。它不直接执行模型生成的任意脚本，而是把声明式计划编译为受控的请求行为，并在 Docker 内隔离运行；若沙箱镜像不可用，则抛出安全违规而非降级到宿主机执行。
  • Evaluator 用于解释过程与生成反馈，但不拥有最终成功裁决权。它的 detected_primitives、confidence、summary 等字段是解释性文本，不构成证据；最终是否成功由 GoalVerifier 决定。
  • GoalVerifier 是确定性裁决器，不在 LLM 推理路径内。它只从当前轮执行结果的允许证据源中取证，限 chain_output._last_response_text、_http_responses[*].response_body 与 http_responses[*].response_body；显式排除 Planner rationale、计划正文、历史 memory 与旧 workspace 文件；同时以回显排除防止将请求内字符串误判为服务端产出。
  • GoalVerifier 命中后 Coordinator 立即结束迭代。GoalVerifier 在 Evaluator 之前运行（coordinator.py:1164）；命中后直接 return 0，不调用 Evaluator、不进入下一轮 Planner、不增加迭代预算。若未命中，则正常回落到 Evaluator 进行过程解释与反馈生成。

3.5 关键问题复现与迭代修复分析

本节如实记录在原型开发过程中遇到的关键工程问题及其修复思路。这些问题的共同主题是：当"模型说了算"时系统不可信，必须用结构与契约把成功判定从模型主观判断中剥离出来。本节不宣称这些问题已被"彻底解决"，而是说明当前实现采取了哪些可复核的工程措施来降低其影响。

3.5.1 请求契约失配问题

在早期实现中，计划虽然表达了"POST 并携带 text 参数"的意图，但执行层没有把参数可靠地编码为实际请求体，导致服务端只返回默认文本、输入框 value 为空。表象上是"收到了 200"，实质上是请求没有按契约送达。这类问题很难从模型自述中发现，因为模型往往仍会给出乐观的总结。

修复方向是引入物化的请求契约。系统在执行前把请求意图固化为 materialized_execution_record，包含 request_method、request_endpoint、request_parameters、normalized_request_body 及其指纹（request_body_fingerprint、execution_fingerprint）。在本案例的实测产物中可以看到：方法为 POST、端点为 /、参数列表为 ["text"]、规范化请求体为包含 text 字段的表单。这样，请求的方法、路径、请求体与漏洞线索是否一致，变成可逐字段比对的事实，而不是靠模型口述。当响应体仍是空参数默认页时，系统据此判定"参数未送达"而非"漏洞不存在"。

3.5.2 AST 模式兼容与可执行性问题

结构化计划中的步骤 command 字段可能为空（声明式步骤依赖结构化请求描述而非内联代码）。旧代码若默认把 command 当作字符串处理，会出现归一化与执行异常。这一问题若不处理，声明式计划将无法安全落到沙箱执行。

修复方向包括 None-safe 归一化与结构化编译：对空 command 做安全占位而非崩溃；当步骤携带结构化请求描述时，由 Executor 将其编译为受控的请求脚本，而非直接信任内联代码。Validator 同时对计划做语法树与能力层面审核，确保即便计划以声明式表达，落到执行线上的行为仍受限。该修复使"声明式计划"与"内联代码计划"两条路径都能在沙箱中安全执行，且前者在审计上更清晰。

3.5.3 长上下文与提示词预算问题

Planner 的输入包含静态漏洞线索、能力约束、历史反馈、已验证事实与用户目标等多源信息。当这些内容过长时，关键的请求契约信息会被稀释，甚至出现 schema 截断，导致模型忽略 text 参数或端点等关键事实。这是大模型 Agent 的共性难题。

本系统采取的改进原则包括：对历史信息按优先级保留，关键请求契约优先于过程性叙述；对冗长条目做整条目压缩而非截断中段，以保留语义完整性；设置终止条件与无进展熔断，避免在已无新信息时无限消耗预算。需要说明的是，这些措施是工程上的缓解，本报告不宣称"数学上绝对聚焦"，也不宣称"物理截断完全解决幻觉"；模型输出的不稳定性仍然存在，系统通过 Validator、契约、沙箱与 GoalVerifier 来降低其影响，而非声称消除。

3.5.4 成功判定与停止机制问题

这是本章最重要的问题。在早期实现中，成功判定高度依赖 Evaluator 的主观总结：即使当前 HTTP 响应中已经出现目标证据，若 Evaluator 只查看了被截短的 stdout 或基于历史记忆给出乐观/悲观结论，仍可能写出失败判断，导致系统在已经成功的状态下继续循环；反之，模型也可能在缺乏目标证据时虚报成功。两个方向都会造成"已成功仍继续跑"或"未成功却宣布完成"的失控。

当前的修复围绕"把成功判定从模型主观判断中剥离"展开，具体包括：

  • 引入独立于 LLM 的确定性目标裁决器 GoalVerifier：作为 b/core/goal_verifier.py 中的独立模块（verify_goal()），它只扫描当前轮执行结果中的允许证据源（chain_output._last_response_text、_http_responses[*].response_body、http_responses[*].response_body），不与 LLM 共享推理路径，也不依赖 Evaluator 的任何输出。
  • 限定允许证据源、显式排除污染源：裁决只从当前轮的执行结果中取证；显式排除 Planner rationale、计划正文、历史 memory、上一轮 feedback 与旧 workspace 文件。
  • 零信任覆写：当模型声称成功但当前轮证据中未出现约定目标标记时，系统强制降级为失败；反之，当本地检测到目标标记时，强制确认为成功。这一覆写以代码事实为准，覆盖模型的乐观或悲观倾向。
  • 回显排除（Anti-Echo）：为避免把请求中自带的字符串误判为服务端产出，GoalVerifier 从计划中提取已发送的载荷字段（body、query、data、params、payload、command），在进行 flag 匹配时排除仅在请求中出现而未在响应中出现的字符串。
  • 命中即停，Evaluator 在成功路径上完全跳过：GoalVerifier 在 Evaluator 之前运行（coordinator.py:1164）；命中后 Coordinator 执行 return 0 立即结束迭代——不产生 Evaluator LLM 调用、不写入可能覆盖客观结论的 feedback、不进入下一轮 Planner、不增加迭代预算。Victory Screen 写入 success_summary.json 并渲染胜利结算 HUD。

3.6 测试结果与分析

在本次测试中，系统对表 3-1 所列 5 个典型入门级 Web 挑战均完成了端到端受控验证，验证结果均为通过。本节以案例验证结果与工程性质验证的方式给出结论。

以 Labyrinth Linguist 为例，实测产物呈现出一条连贯的证据链：Planner 输出结构化计划；Validator 核验通过并产出 validated_plan.json；Executor 在 Docker 沙箱中执行，产出 execution_result.json（包含物化请求契约、结构化 HTTP 响应体与执行指纹）；在某一轮执行中，当前轮真实 HTTP response body 出现最终目标证据；GoalVerifier 以 verify_goal() 扫描允许证据源，匹配约定目标标记并完成回显排除；裁决命中后 Coordinator 写入 success_summary.json（验证版本 goal-verifier-v1，来源类型 chain_response_body，含证据哈希），渲染 Victory Screen 并执行 return 0 立即停止，Evaluator 被跳过。其余 4 个挑战亦沿同一受控闭环完成验证。

据此，本章给出以下定性结论：

  • 结构化请求能够按约定将参数送到目标：物化请求契约与实际 HTTP 响应一致，参数送达可在响应中验证。
  • 系统能区分"HTTP 成功"与"漏洞目标成功"：200 仅被归入"请求可达"，目标成功需由 GoalVerifier 从允许证据源独立确认。
  • Validator 可在执行前阻断不满足结构化/契约要求的计划：语法、能力与契约不合规的计划不进入沙箱。
  • GoalVerifier 在 Evaluator 之前运行，可在当前轮完整响应中独立确认目标：裁决基于实际响应体与回显排除，不受模型主观判断影响；命中后 Evaluator 被跳过。
  • 成功后执行立即结束：GoalVerifier 命中后 Coordinator return 0，不进入下一轮 Planner、不增加预算。
  • 失败时仍保留完整产物链：plan、validated_plan、execution_result、feedback 均落盘，便于复盘。

上述结论均为定性结论，聚焦于闭环能力本身的工程有效性。系统在部分运行中也会因模型输出不稳定、目标不可达或契约失配而未能推进到目标层；这些情形同样被产物链完整记录，作为迭代改进的依据。

3.7 测试边界与未来增强方向

本节以专业口径说明当前测试的边界与后续增强方向，作为系统持续演进的指引。

第一，本次测试聚焦于 5 个典型入门级 Web 安全挑战，已完成端到端受控验证，覆盖多个典型 Web 验证场景。

第二，GoalVerifier 当前适配 Flag / 明确目标标记模式，其目标确认依赖约定格式的目标字符串与确定性扫描；面向企业环境时，可将裁决器扩展为业务影响验证器，以"业务影响"作为最终目标证据，这是后续面向企业落地的重要增强方向。

第三，LLM 输出存在固有不稳定性，模型可能忽略关键参数、误判响应或给出与事实相悖的总结。本系统通过 Validator、请求契约、Docker 沙箱与 GoalVerifier 形成多层约束来降低其影响；GoalVerifier 在 Evaluator 之前运行并以 return 0 直接结束，确保成功路径上不产生 LLM 调用、不存在被模型主观判断覆写客观结论的可能。

第四，动态重规划、Skills、MCP 集成、Flow 持久化等属于后续扩展方向，将在继承现有 AST 校验、请求契约、Docker 隔离、FSM/EPE 与 GoalVerifier 等约束的前提下逐步引入，不以开放宿主机 Shell 为代价。

第五，沙箱安全将持续硬化，后续将在现有容器隔离基础上引入额外系统调用过滤与资源控制措施，进一步提升执行边界的强度。

第四章　创新性说明

本章相对"常规 LLM Agent / 自动化扫描工具"说明本作品的具体创新点，并以上述 5 个挑战的端到端受控验证作为工程验证支撑。

4.1 从自由文本执行到声明式受控执行

传统 Agent 往往直接让模型生成 Shell、Python 或请求脚本并送入执行，执行边界难以审计：模型写什么，系统就跑什么，成功与否依赖模型自述。这种"自由文本执行"模式在面对安全验证这类对正确性敏感的任务时存在根本缺陷——它把"是否成功"这一最关键的判定权交给了最不可靠的一环。

本作品的创新不在于"使用了语法树"这一具体技术，而在于把执行模型从"模型提议即可执行"转变为"模型提议动作 ≠ 动作天然可信"。系统要求：模型提议的动作只有依次通过结构校验、能力校验、目标校验与参数契约校验之后，才可被编译为受控执行。Planner 输出结构化计划，Validator 校验其语法树与能力白名单，Executor 把声明式请求描述编译为结构化的 HTTP 行为并在沙箱中执行。这样，执行线上发生的事情始终是可预测、可审计的。

结合本案例可以看清这一创新的价值：form body 与 text 参数不再以自然语言"我希望 POST 一个 text 参数"来表达，而是被固化为物化请求契约——方法、端点、参数列表、规范化请求体及其指纹。"请求意图"与"真实线缆行为"之间的一致性因此变成可逐字段比对的事实。当二者不一致时，系统在执行前或执行后都能发现，而不是任由模型给出一个看似合理的总结。

4.2 将漏洞验证建模为有限状态机推进

本作品把漏洞验证过程建模为有限状态机（FSM）的逐级推进。在当前实现中，能力推进序列的语义进程为：init（初始）→ probe_success（目标可达、探测成功）→ payload_injected（载荷注入、参数送达）→ gadget_triggered（利用原语被触发、漏洞机制被观察到）→ oob_received（OOB/带外证据或能力影响被确认）。当 GoalVerifier 从当前轮真实响应中确认目标证据后，状态跳转至终态 objective_verified（coordinator.py:1176），系统立即结束迭代。

FSM 解决的核心问题不是"多画几个状态"，而是防止验证过程在不满足前提时跳级。具体而言：它避免在尚未确认参数送达时就声称利用成功；避免仅凭 HTTP 200 就把状态推高到原语层；让下一轮计划受到当前已确认状态的约束。状态推进需多次确认方可稳定，但 objective_verified 作为终态由 GoalVerifier 一次命中即确认，直接触发 return 0。

4.3 EPE：以证据层级替代二元成功/失败

EPE（Evidence-Progressive Evaluation，证据渐进评估）是本作品对"成功/失败"这一二元判定的替代方案。它把漏洞利用过程建模为证据强度的逐级递进。在代码中（b/agents/evaluator.py），EPE 对应四层信号权重：L1 表层信号（如响应长度变化、错误触发、载荷回显）、L2 原语信号（如 SSTI 回显、OOB 尝试）、L3 能力信号（如命令执行、任意文件读取）、L4 目标信号（如目标标记确认），并通过 progress_score 等量化字段反映当前证据层级。

这一层级思想在本案例中体现得尤为清晰：

  • HTTP 200 仅表示服务可达：归入表层，不代表参数送达或原语触发。
  • 返回默认页面、输入框为空：说明参数可能未送达，状态不应上升。
  • 低风险表达式求值结果回显：说明模板引擎发生了解析与求值，进入原语层（对应 FSM 的 gadget_triggered）。
  • 当前轮完整响应中的目标标记：由 GoalVerifier 独立确认，跳转至终态 objective_verified 并触发即时停止。

EPE 的工程价值在于为系统提供分级决策依据：它帮助系统区分"应当修复请求""应当停留在验证""应当继续受控推进"与"应当立即结束"。当证据仅停留在表层时，系统不会贸然推进到能力层；当原语已确认时，系统才考虑下一步受控推进；当目标层证据出现并被 GoalVerifier 确认时，系统立即终止。这种分级替代了"模型说成功就成功"的脆弱判定，使整个过程具备可解释的渐进性。

4.4 确定性目标裁决器与反历史污染成功判定

本作品与一般 Agent 最大的差别，在于成功判定权被从模型手中剥离并交给独立于 LLM 的确定性目标裁决器 GoalVerifier。其设计要点如下。

第一，Planner 不可宣布成功。Planner 只产出结构化计划，其 rationale、chain_design 等字段属于意图与推理文本，不构成证据。第二，Evaluator 不拥有最终裁决权。它的 detected_primitives、confidence、summary 仅为解释性文本，绝不创造证据；GoalVerifier 在 Evaluator 之前运行，命中后 Evaluator 被完全跳过。第三，历史 memory 不可作为当前成功证据。GoalVerifier 只采信当前轮真实执行响应，防止跨轮污染导致的"记忆式成功"。第四，只有当前轮真实执行响应可触发目标确认；同时采用回显排除（anti-echo），从已发送载荷中提取 body/query/data/params/payload/command 字段进行交叉比对，防止把请求内字符串误认为服务端产出。第五，一旦 GoalVerifier 命中，Coordinator 执行 return 0 立即结束——不调用 Evaluator、不进入下一轮 Planner、不增加迭代预算。Victory Screen 写入 success_summary.json（含验证版本 goal-verifier-v1、目标证据、证据哈希与来源类型）并渲染胜利结算 HUD。

GoalVerifier 是一个确定性裁决器，而不是"再调一个大模型来判"。它以纯代码逻辑扫描允许证据源，不与 LLM 共享推理路径，也不受模型主观判断的任何影响。这种"独立裁决器"而非"又一个 Agent"的架构选择，是本作品与一般多 Agent 框架最根本的区别。

4.5 工程创新：请求契约、目标锁定与可审计产物链

本作品在工程层面有三项相互配合的创新，它们共同支撑了上述机制的可落地与可审计。

第一，请求契约。系统把 endpoint、method、parameter、body format 从自然语言意图变为可校验的结构化约束，并以物化请求契约（含请求体指纹与执行指纹）固化。这使得"请求是否按漏洞线索送达"成为可逐字段比对的事实，而非模型口述。请求契约同时为 GoalVerifier 的回显排除提供了依据——系统知道请求里发了什么，才能判断响应里的内容是不是服务端产出。

第二，Target Context Lock。授权目标在系统启动时即被锁定：协议校验、主机名校验、DNS 解析与 URL 规范化后固化 base_url，Executor 仅使用该锁定地址。这一机制避免模型在规划过程中自行扩大网络范围，把执行边界约束在授权靶场之内。

第三，可审计产物链。plan.json → validated_plan.json → execution_result.json → feedback.json / success_summary.json + Victory Screen 共同构成一条可复盘的证据链：意图→准入→执行→判定→结论→胜利结算，每一步都落盘、可追溯。即便某次运行失败，也能从产物链中定位是契约失配、原语未触发还是模型误判，为迭代改进提供依据。success_summary.json 中的 verified_by、evidence_sha256、source_kind 与 artifact 字段为成功结论提供可独立复核的客观记录。

4.7 可扩展性与未来方向

以下方向均属未来路线，在现有架构之上扩展，且必须继承 AST 校验、请求契约、Docker 隔离、FSM/EPE 与 GoalVerifier 等已有约束，不以开放宿主机 Shell 为代价。

  • Flow 持久化：将验证流程的状态与中间证据持久化，支持跨会话续跑与中断恢复。
  • 受限 ToolCatalog：在受控前提下引入受限工具目录，扩展可验证的漏洞类型。
  • 审核型 Skills：以可审核的技能模板承载常见验证模式，技能本身须经校验方可使用。
  • 安全 MCP Bridge：通过受控的 MCP 桥接外部能力，桥接层保留审计与契约约束。
  • 企业目标 GoalVerifier：将当前适配 Flag/明确目标的裁决器扩展为业务影响验证器，以适用企业环境。
  • 可视化验证报告：在现有产物链与 Victory Screen 基础上生成面向人类的可视化报告，提升复盘效率。

上述扩展不会放松现有的安全边界。无论功能如何扩展，系统都将坚持"模型提议 ≠ 动作可信"的根本立场，所有执行仍须经声明—校验—编译—执行—裁决的受控闭环，沙箱隔离与目标锁定不被牺牲。
